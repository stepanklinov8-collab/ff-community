# Безопасная основа для следующих обновлений

Этот проект разделяет существующий сайт и новые функциональные разделы. Новая возможность получает собственную папку в `src/modules/<имя>`, страницу и API с обязательной проверкой режима. Общие элементы сайта остаются в основном приложении и подключаются через публичный интерфейс модуля.

## Локальная работа

Обычный `npm run dev` запускается в изолированной локальной среде на `127.0.0.1:3000`. Он очищает унаследованные ключи Supabase, Firebase, OpenAI и планировщика и использует безопасные тестовые значения. Это предотвращает случайное подключение рабочей базы из `.env.local`.

Для проверки production-сборки используются `npm run build:test` и `npm run verify`. Они не подключаются к Supabase: база в SQL-проверках создаётся локально в памяти, а внешние отправки отключены.

## Режимы разделов

Переменная `OMCITE_MODULES` принимает точные пары `имя=режим`, разделённые запятыми:

- `off` — раздел и его API закрыты;
- `preview` — раздел доступен только администраторам и суперадминистратору;
- `public` — раздел доступен всем.

Неизвестные, дублированные и неправильно записанные значения закрываются автоматически. Фоновая задача модуля запускается только в режиме `public`; в режиме предварительного просмотра она выключена.

Создать заготовку можно командой `npm run module:create -- team-news --dry-run`, а после проверки — без `--dry-run`. Генератор не перезаписывает существующие файлы и не принимает пути с обходом каталога.

## Границы и производительность

Проверка `npm run check:boundaries` не разрешает модулю импортировать внутренности другого модуля, прямые клиенты базы, Firebase Admin или общие CSS-файлы. Серверные операции проходят через `src/platform/database.ts`, а клиентские компоненты не могут импортировать серверные сервисы.

Новые страницы не добавляются в общий загружаемый набор без необходимости: навигация получает только список доступных модулей, API модуля вызывается при открытии соответствующего раздела, ответы приватных API не кэшируются общим кэшем. Тяжёлые запросы и расчёты должны выполняться постранично или через заранее рассчитанные агрегаты.

## Выпуск

Перед изменением рабочей базы должны быть выполнены:

1. `npm run verify` и `npm run test:browser`;
2. проверка миграции в тестовом проекте и обратимого сценария;
3. свежий полный резервный экспорт рабочей базы, проверка хеша и восстановление в отдельном тестовом проекте;
4. проверка сборки и переменных окружения в preview;
5. ревью изменений и прохождение обязательной CI-проверки `Verify site`.

Миграции рабочей базы намеренно требуют явного указания production-проекта и подтверждения проверенного восстановления. Неполный или устаревший экспорт не считается резервной копией и не даёт права продолжать выпуск.

На текущем этапе полный экспорт рабочей базы ещё не подтверждён: `pg_dump` через Supavisor обрывает соединение на чтении системного каталога, хотя отдельный запрос к тому же каталогу проходит. Поэтому рабочая база этим обновлением не изменялась, а ветка не считается готовой к production-выпуску до успешного экспорта и восстановления в отдельном проекте.

Эта основа снижает область отказа и защищает данные, но не обещает абсолютное отсутствие ошибок. Для каждой новой функции нужны собственные проверки доступа, миграций, ограничений запросов и пользовательских сценариев.

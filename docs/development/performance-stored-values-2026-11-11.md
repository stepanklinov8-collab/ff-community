# Подготовка ускорения: 11 ноября 2026

Запрос: сохранять рассчитанные рейтинг/стоимость после изменения результатов, не рассчитывать при просмотре; ускорить прокси; сохранять фотографии в кэше с прежним качеством. Пользователю сказано, что изменения готовятся локально. **Эта оптимизация не опубликована.** Шаблоны договоров по-прежнему отложены и не входят в публикацию оптимизации.

## Что найдено

Рейтинг уже хранится в `competition_ratings`/`profiles`/`teams`; при чтении рейтинга тяжело пересчитывалась прежде всего стоимость. `u2_leaderboard` вызывает `u2_cost_for_target`, который снова вычисляет `u5_player_value_exact`/`u5_organization_value_exact`, включая историю и цены участников. Существующий 30-секундный серверный кэш скрывает стоимость повторных чтений, но не первого запроса. База — eu-west-1 (Ирландия), функции сайта — iad1 (США). В замерах прокси добавлял 0,3–0,4 с; первый рейтинг занимал 6,1 с, прогретый около 0,23 с. Исходники отдельных изображений 1–2,3 МБ. Измерения одной сети не являются гарантией времени для всех пользователей.

## Изменения

- `202611110002_stored_economy_values.sql`: точная цена сохраняется в закрытой `economy_value_cache`; существующие функции чтения возвращают число, не вызывают расчёт при отсутствии строки (нет скрытого медленного fallback).
- Одобренные формулы переименованы в закрытые расчётные функции без изменения математики. Организации используют точные сохранённые цены всех участников до округления; итог округляется прежним `u2_cost_for_target`.
- Данные пересчитываются в конце транзакции изменения, один раз, через deferred trigger. Сначала затронутые игроки, затем организации; ошибка расчёта откатывает исходное изменение и цену вместе. Новые цифры уже сохранены к моменту ответа публикации.
- Учтены публикация/исправление/удаление результатов, факты/прежняя статистика, смена состава, точного рейтинга, репутации, веса/правил события, отмена/перенос сессии и этапа, MVP/достижения, прогнозы. Нормальное редактирование ника, контакта, аватарки, комнаты, описания не запускает формулы.
- Добавление нового этапа и изменение только его source_session_id тоже обновляют прежние призовые оценки: это может изменить призовую допустимость ранее одноэтапного турнира. Отдельный SQL-сценарий проверяет снижение и восстановление цены, не только время обновления строки.
- При изменении рейтинга организации пересчитывается относительная надбавка других организаций (общий знаменатель); новый участник с нулём не требует общего полного пересчёта игроков. На страницу отдаётся сохранённая цена. Для прочих режимов историческая формула прежняя (основной договорённый рынок — main).
- `vercel.json`: подготовлен регион `dub1`, совпадающий с регионом базы. Вступит в силу только после деплоя; менее 0,1 с по всем сетям не обещано.
- Gateway: публичные изображения без пользовательского JWT/cookies; неизменяемые UUID-пути — browser/CDN cache до года, старые имена — 1 час с ETag/Last-Modified и 304. Ошибки, Auth/REST/профили/балансы остаются no-store. HTML/SVG под видом картинки не допускаются. Исходные байты не изменяются.
- Загрузка аватарки/обложки использует новый UUID и upsert=false при каждой замене; новый URL сразу выбирает новую картинку. Для новых загрузок Cache-Control также сохраняется в Supabase. Старые сохранённые URL в БД не переписываются.

## Проверка

На отдельной staging-базе миграция установлена после репетиции с ROLLBACK. Все точные цены до/после совпали; полные контрольные суммы coin_accounts, coin_entries, profiles, teams, competition_ratings совпали. EXPLAIN ANALYZE рейтинга организаций: до 262,555 / 180,943 / 182,190 мс; после 27,030 / 25,962 / 26,155 мс (примерно в 7 раз быстрее для типичных повторов на этих данных). Это время SQL, не полная задержка пользователя. Production не изменён.

Отдельно проверен обратный SQL `tools/database-tests/rollback-stored-values.sql` внутри транзакции с ROLLBACK: исходные формулы восстановились с теми же ценами, после репетиции тестовая оптимизация осталась установлена. Защищённый staging-скрипт: `stored-values-staging.mjs --apply` / `--verify-rollback`.

Production-сборка, 101 доменный тест, lint и проверка границ модулей прошли. Все 8 браузерных сценариев прокси прошли, включая HTTP-кэш между перезагрузками страницы и загрузку нового UUID. При очистке браузером кэша/в режиме инкогнито изображение потребуется получить снова; гарантировать вечное хранение на устройстве нельзя.

Общий SQL-набор завершился успешно (`stored-values-full-sql.log`); после уточнения обработки нового этапа повторно прошёл целевой набор (`stored-values-focused.log`), staging-триггер синхронизирован. Существующий тест сравнения MVP-цен внутри откатываемой транзакции теперь явно делает `SET CONSTRAINTS ALL IMMEDIATE` перед чтением: так он проверяет значения после завершения расчёта, как при настоящем commit, сохраняя возможность rollback фикстуры.

Локальный smoke против настоящей тестовой базы также прошёл: авторизация, основной кошелёк, организации, чат, ноль прямых Supabase-запросов/WebSocket браузера; сообщения и деньги не отправлялись. `/api/competition/leaderboard?mode=main&type=team&limit=100`: HTTP 200, 303 / 21 / 25 мс (первый/два повторных запроса; dev на ПК, не production SLA). Локальный сервер оставлен на `http://127.0.0.1:3001`.

## Порядок выпуска

Сначала проверить/backfill миграции сохранённых цен на тестовой базе, сравнить все точные цены/рейтинги с прежними функциями и сохранить откат. Затем отдельный релиз только файлов ускорения и миграции, без отложенных контрактных шаблонов. Балансы и выплаты не меняются. Запуск расчётов на личном ПК не нужен: транзакционный расчёт в базе не зависит от доступности ПК и исключает неполные результаты.

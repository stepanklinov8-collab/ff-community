# Доступ к Supabase через сайт — 6 ноября 2026

## Объём и переключение

Отдельная ветка `codex/supabase-gateway`. Базовая рабочая версия до изменения — `9d5502e04a7ee972c93207ea34d68d35c887d331`, Vercel deployment `4uwvRnGEe44BwjrWLvNJF3JhMEzz` (https://ff-community-pgksare0m-ff-community.vercel.app).

Локальная контрольная метка: `codex/pre-backend-proxy-20261106`.

`NEXT_PUBLIC_SUPABASE_TRANSPORT=proxy` включает шлюз `/api/backend/...`. Значение `direct` возвращает прежний маршрут и отключает шлюз. Изменение флага требует новой сборки/деплоя: публичный флаг встраивается в клиентский код. Автоматического переключения после неясного ответа сервера нет, чтобы повторно не выполнять регистрацию или изменение данных.

Если флаг не задан, production/development/test работают как прежде (`direct`), а Preview использует `proxy` для безопасной проверки на staging. Явное значение флага имеет приоритет. Тесты и обычный dev сбрасывают унаследованные настройки и ключи; локальный запуск со staging: `node tools/database-tests/start-contract-staging.mjs --backend-proxy`.

## Что меняется

- SDK сохраняет исходный URL проекта, имя cookies и механизм сессии. Его HTTP-запросы из браузера проходят через собственный домен. Серверные запросы продолжают обращаться к Supabase напрямую.
- Регистрация, password/refresh token, проверка кода, resend/recover/logout/user доступны через строго ограниченные маршруты. Административные Auth API и произвольные внешние URL не проксируются.
- REST/RPC получает исходный JWT пользователя и только публичный ключ проекта. Права/RLS не расширяются, служебный ключ в шлюзе не используется. Cookies сайта не пересылаются в Supabase.
- Auth/REST ответы не кешируются. Ограничены тело запроса, длительность и редиректы. Ошибки соединения не раскрывают тело исключения, пароли или токены.
- Публичные изображения из `avatars`/`event-images` проходят через тот же домен с исходными байтами и качеством. Изображения других источников не меняются. HTML/SVG под видом картинки не выдаются с домена приложения. В БД остаются прежние URL.
- В proxy-режиме чат не открывает прямые WebSocket-соединения с Supabase. Новые сообщения проверяются раз в 10 секунд, только на видимой странице; отправка идёт через прежний API и не ждёт таймера. В direct-режиме остаётся Realtime с прежним резервным обновлением.
- Рабочие шаблоны confirmation/recovery уже используют `/auth/confirm` с `TokenHash` и кодом. Это проверено чтением настроек; SMTP и шаблоны production не менялись. На staging стандартные шаблоны отличаются: фактическую отправку новых писем в этом выпуске не выполнять без отдельного сценария.

## Откат

1. Для немедленного возврата в Vercel восстановить указанную выше предыдущую production-публикацию (Instant Rollback/Promote по возможностям аккаунта). Её код совместим с текущей базой.
2. Чтобы оставить новый код с прежним маршрутом, установить Production `NEXT_PUBLIC_SUPABASE_TRANSPORT=direct` и сделать новый деплой основной ветки. Нельзя просто выключить серверный маршрут без пересборки браузерного кода.
3. Не менять `NEXT_PUBLIC_SUPABASE_URL`, публичный ключ, cookies или таблицы. Миграций, переноса пользователей/денег и переписывания URL нет; обратный SQL не нужен. Уже открытые старые вкладки могут потребовать обновления страницы после смены публикации.

## Проверки

Команды: `node --test tests/backend-gateway.test.mjs`, `node scripts/verify.mjs`, `npm run test:browser`, `node scripts/build-gateway-test.mjs`, `npx playwright test --config playwright.gateway.config.ts`.

Отдельные браузерные сценарии блокируют прямые обращения к Supabase и проверяют signup/verify, password login/logout, refresh, REST, изображения, recover/update password, ссылку подтверждения и чат без WebSocket. Обычный набор отдельно проверяет прежний direct-режим. Настоящий staging smoke — `node tools/database-tests/smoke-backend-proxy.mjs`: тестовый аккаунт, чтение кошелька/организаций/чата, без отправки сообщений, писем или изменения балансов.

Локальные измерения не доказывают доступность у конкретного провайдера. Перед включением production нужен тест Preview без VPN на сети одного из затронутых пользователей, а после включения — контроль auth-ошибок и времени запросов. Платный AdGuard/VPS для этой схемы не используется.

Итог локальной проверки 6 ноября: полный verify прошёл (97 доменных тестов, SQL-набор, ESLint, TypeScript, сборка); 146 существующих браузерных сценариев прошли в direct-режиме, 7 дополнительных — в proxy-режиме с запретом прямого доступа. Настоящий staging smoke успешно открыл кошелёк, организации и чат без прямых Supabase HTTP/WebSocket: sign-in 695 мс, три прогретых чтения пользователя 166/183/181 мс. Эти значения измерены локально с данного подключения. Внешние сообщения/письма и денежные операции не выполнялись. Доказательства лежат в игнорируемом `artifacts/contracts/backend-staging-smoke.json`.

## Согласованный объём

1. Карточка даты на главной передаёт `sessionId` на страницу мероприятия. Выбор даты сохраняется в адресе; прямые ссылки раскрывают нужную прошедшую/будущую сессию.
2. Результаты без `sessionId` выбирают последнюю опубликованную сессию по дате её проведения. Позднее исправление старой сессии не делает её последней. Явная ссылка на неопубликованную сессию показывает ожидание, на чужую/отменённую — ошибку. Переключение даты обновляет URL и загружает соответствующие результаты; ошибка имеет кнопку повторения.
4. Одна боковая панель разделена на «Играть», «Моя арена», «Сообщество», «Управление и помощь». Модульные ссылки загружаются одним запросом для всех групп. Прежние ссылки и проверка доступности модулей сохранены; «Входящие сообщения» отделены названием от «Чата» и уведомлений.
5. Конструктор договора разбит на стороны, срок, выплаты, ограничения и проверку. Значения сохраняются между шагами; есть полный режим для опытных пользователей. Перед сохранением видны стороны, условия и начальные денежные обязательства; зарплатный резерв обозначен с учётом возможного неполного периода. Окончательная сумма проверяется существующим финансовым движком при подписании. Формат подписанных условий и расчёты выплат не менялись. **Шаблоны не выдумываются: пользователь ещё подготовит свои тексты и условия.**
6. До отправки заявки показываются существующие ограничения организации и выбранных участников её постоянного состава: причина, срок, область действия, предупреждения-основания, ссылки на событие и обжалование. Проверять чужую организацию без полномочий или произвольные аккаунты через URL нельзя. Гостевой допуск и окончательная проверка всех игроков остаются в действующих RPC регистрации; отсутствие предупреждения в предварительной справке не является разрешением регистрации. Правила, сроки и накопленные предупреждения не изменяются.
7. В мобильной таблице результатов закреплены место и название, обозначена горизонтальная прокрутка. Подробности вынесены из закреплённой ячейки в отдельную строку, числовые столбцы выровнены. Качество и адреса изображений не уменьшались.

## Как сокращена загрузка

- API результатов получает список сессий и лёгкие отметки публикации, затем один опубликованный снимок и игры/группы выбранной сессии. Вместо трёх запросов на каждую сессию — три запроса подробностей одной сессии, плюс метаданные; последние читаются порциями по 200 ID.
- Заявки и снимки составов основной страницы фильтруются `sessionId`. Счётчики `12/12` и запаса всех дат вычисляет одна SQL-агрегация без передачи исторических составов. Старые потребители API без параметра совместимы.
- Карты загружаются для видимых карточек; раскрытие архива подгружает недостающие игры. Кэш существует только в экземпляре страницы и изолирован по событию. У скрытого архива нет запросов игр и комнат.
- Публичное описание и расписание не ждут загрузки личных организаций. Ошибки имеют повтор; у чтения есть таймауты, отмена и защита от устаревшего ответа.
- Проверка пользователя объединяется только на время одновременного запроса с тем же токеном. При смене аккаунта старый ответ отбрасывается. Сервер повторно использует роли исключительно внутри того же объекта `Request` через `WeakMap`, а следующий HTTP-запрос проверяет права заново. Финансовые операции не кэшируются и не объединяются.

Время реальной загрузки зависит от сети и Supabase. Процент ускорения по искусственным задержкам не заявляется; браузерные тесты проверяют состав и количество запросов.

## Порядок публикации и отката

1. Зафиксировать проверенные исходники. Выполнить `node tools/database-tests/plan-optimization-release.mjs --backup=tools/database-tests/artifacts/release-backup/2026-11-01T21-46-22-574Z`. Команда только читает production и готовит приватный SQL/план; DDL не исполняет. Требует чистый Git, свежую копию (до 24 часов), успешное восстановление и совпадение SHA обоих SQL-файлов. Если срок прошёл, создать новую копию и повторить rehearsal с `--rehearse-optimization --run`.
2. После команды пользователя на публикацию проверить отсутствие новых миграций/изменения исходников и актуальность proof. Сначала выполнить подготовленные миграции на точно указанном production-проекте одной транзакцией с записью журнала; сверить защищённые агрегаты.
3. Затем опубликовать проверенную версию приложения. `chat=public,contracts=public` сохранить; экспериментальный дизайн и Кай не включать. Проверить главную ссылку на дату, последние результаты, вход, кошелёк/AP, аналитику администратора и закрытый доступ обычного пользователя.
4. При ошибке публикации вернуть предыдущую версию приложения. Новая функция счётчиков не меняет старые обработчики и может остаться установленной. Финансовые таблицы и данные пользователей не откатывать целиком поверх свежих операций. Если откат отключит ежедневную очистку аналитики, продолжить 90-дневную очистку отдельно либо согласованно удалить только её таблицы; удаление не должно затрагивать кошельки или договоры.

Не запускать старый `apply-contract-release.mjs`: он относится к завершённому выпуску из 55 других миграций. Не повторять начальное начисление миллиона создателю.

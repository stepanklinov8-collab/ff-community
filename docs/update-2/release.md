## Повторить локальные проверки

Node.js 24, зависимости из lock-файлов:

```powershell
npm ci
npm ci --prefix tools/database-tests
node --disable-warning=MODULE_TYPELESS_PACKAGE_JSON --test tools/database-tests/domain.test.mjs
node tools/database-tests/verify.mjs
npm run lint
npm run build
npm audit
```

Для сборки нужны `NEXT_PUBLIC_SUPABASE_URL` и `NEXT_PUBLIC_SUPABASE_ANON_KEY`; в проведённой проверке использовались фиктивные локальные значения. Реальные ключи не хранятся в коде. Для настоящего локального подключения использовать отдельный тестовый Supabase и `.env.local`, а не рабочую базу для пробных публикаций.

`node tools/database-tests/dry-run.mjs` читает только уже имеющийся локальный снимок в `artifacts/live-copy` и не имеет сетевого клиента. `export-readonly.mjs` предназначен исключительно для GET-only выгрузки разрешённых таблиц; порядок получения нового снимка описан в самом файле, секреты не выводить.

## Порядок выпуска после разрешения

На время миграции остановить изменяющие данные старые обработчики/публикации. Сделать актуальную резервную копию. Применить миграции, полный перерасчёт и совместимую сборку как один согласованный выпуск. Не оставлять старое приложение работающим с новым способом записи результатов. Включить обслуживание, выполнить короткую проверку чтения/прав, затем открыть запись.

Отчёты миграции, полный JSON снимка, ключи и документы со скрытыми коэффициентами не публиковать на сайте.

## Восстановление

При сбое до возобновления пользовательской записи восстановить совместимую пару приложения и резервной базы по процедуре хостинга. Не использовать массовый `DROP` новых таблиц или обратную миграцию поверх уже появившихся публикаций/финансовых проводок. Если новые операции уже приняты, сначала сохранить их и согласовать план исправления; возврат старой сборки сам по себе не является восстановлением данных.

# Локальная проверка и будущий выпуск

Обновление подготовлено локально. 24.09.2026 владелец разрешил деплой при полной готовности по ТЗ. Проверка `deployment-readiness.md` выявила незакрытые условия выпуска; рабочую базу и действующий сайт не изменяли. После успешного прохождения условий повторное общее разрешение не требуется.

## Повторить локальные проверки

Node.js 24, зависимости из lock-файлов:

```powershell
npm ci
npm ci --prefix tools/database-tests
node --disable-warning=MODULE_TYPELESS_PACKAGE_JSON --test tools/database-tests/domain.test.mjs
node tools/database-tests/verify.mjs
npm run lint
npm run build
npm audit
```

Для сборки нужны `NEXT_PUBLIC_SUPABASE_URL` и `NEXT_PUBLIC_SUPABASE_ANON_KEY`; в проведённой проверке использовались фиктивные локальные значения. Реальные ключи не хранятся в коде. Для настоящего локального подключения использовать отдельный тестовый Supabase и `.env.local`, а не рабочую базу для пробных публикаций.

`node tools/database-tests/dry-run.mjs` читает только уже имеющийся локальный снимок в `artifacts/live-copy` и не имеет сетевого клиента. `export-readonly.mjs` предназначен исключительно для GET-only выгрузки разрешённых таблиц; порядок получения нового снимка описан в самом файле, секреты не выводить.

## Обязательные проверки перед деплоем

1. Получить полный резервный снимок SQL/данных/Storage и развернуть отдельную staging-копию. Проверить актуальность базы относительно коммита, с которого начата работа.
2. На staging применить 26 новых миграций по порядку, затем выполнить `supabase/update-2/recalculate.sql`. Не запускать повторно первоначальные миграции поверх существующего проекта. Пересчёт допускает повторное выполнение; сами новые миграции рассчитаны на однократное применение мигратором.
3. Проверить настоящими отдельными аккаунтами: администратор, организатор, ответственный своей и чужой сессии, участник, анонимный посетитель. Убедиться, что черновики, причины отмены санкций, обращения и пароли чужих комнат закрыты.
4. Проверить приватный bucket `competition-evidence`: 10 JPG/PNG на игру, подписанные ссылки, скачивание ZIP, права ответственного, очистку переигровки и повтор удаления после сбоя. Обложки остаются в `event-images`.
5. Пройти XLSX/CSV импорт и холодный запуск браузерного OCR на реальном скриншоте. Языковые файлы OCR загружаются при первом запуске; текст обязательно подтверждается человеком перед переносом в черновик.
6. Настроить существующий планировщик на защищённый `GET /api/cron/event-notifications` раз в минуту с `Authorization: Bearer <CRON_SECRET>`. Без планировщика не обещать своевременную рассылку, публикацию по расписанию, обновление истёкшей репутации и очистку Storage. Не создавать платную подписку автоматически. Проверить push отдельно; локальные тесты не отправляли внешних сообщений.
7. Проверить публикацию, двойное подтверждение КВ, исправление, отрицательный баланс и восстановление после потерянного ответа через настоящий API. Проверить две одновременно открытые формы, в том числе конфликт версии. Пройти нагрузочный сценарий 1024 участников/много групп.
8. Сопоставить суммы кошельков/ставок, количества истории и отчёт `competition_migration_review` с резервной копией. Если обнаружатся старые неоднозначные БО-рынки без конкретной игры, отдельно согласовать их привязку/расчёт; в изученном снимке таких активных данных не было.
9. Сохранить staging-результат и свежий отчёт распределения. Разрешение владельца от 24.09.2026 действует при успешном завершении проверок: после них применить тот же набор на рабочем окружении. Новые расходы и действия вне согласованного объёма обсуждаются отдельно.

## Порядок выпуска после разрешения

На время миграции остановить изменяющие данные старые обработчики/публикации. Сделать актуальную резервную копию. Применить миграции, полный перерасчёт и совместимую сборку как один согласованный выпуск. Не оставлять старое приложение работающим с новым способом записи результатов. Включить обслуживание, выполнить короткую проверку чтения/прав, затем открыть запись.

Отчёты миграции, полный JSON снимка, ключи и документы со скрытыми коэффициентами не публиковать на сайте.

## Восстановление

При сбое до возобновления пользовательской записи восстановить совместимую пару приложения и резервной базы по процедуре хостинга. Не использовать массовый `DROP` новых таблиц или обратную миграцию поверх уже появившихся публикаций/финансовых проводок. Если новые операции уже приняты, сначала сохранить их и согласовать план исправления; возврат старой сборки сам по себе не является восстановлением данных.
